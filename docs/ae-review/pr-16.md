**opportunities to learn**
- **Generic adapter:** `strict[T any]` turns a typed `func(T) (any, error)` into the untyped `Tool.Run`, so each tool body only sees a checked struct. `schema.go:36`
- **Exact-case keys:** `encoding/json` matches struct keys ignoring case, but map keys keep it. Decoding into `map[string]json.RawMessage` first is how to reject `ItemID`. `schema.go:41`
- **`null` into a `string` is a no-op**, so one `== ""` check covers missing, `null` and `""`. `schema.go:63`
- **Iterators (Go 1.23+):** `slices.Sorted(maps.Keys(m))` gives a fixed order over a map, so the error is the same on every run. `schema.go:45`
- **Breaking an import cycle:** move the shared type (`Tool`) to the side nobody else depends on. Now `agents → tools`, one way. `tools/tool.go:8`
- **Composition over a new type:** `NewSupportAgent` is just `NewAgent` with fixed arguments, with no new struct or interface. `agents/support.go:16`
- **Ordered slice instead of a map** for the knowledge base, because map iteration order is random in Go. `search.go:10`
- **Comparing marshalled JSON** in tests (`checkSpec`, `runTool`) checks what the model actually receives, not the Go values. `helpers_test.go:11`

**error handling**
- **Go internals leak to the model.** A wrong type gives `json: cannot unmarshal number into Go struct field classifyArgs.itemId of type string`. The model sees the private struct name. Wrap it as `"itemId" must be a string`. `schema.go:52`
- **One message, three causes.** Missing, `null` and `""` all give `"itemId" is required`, so the model can't tell that it sent an empty value. Distinct text such as `is empty` vs `is missing` would help. `schema.go:64`
- **A broken schema fails quietly.** `properties, _ := …(map[string]any)` with a failed assertion makes every call fail with `unknown field`, and nothing names the real cause. Panic when the tool is built instead. `schema.go:37`
- **Hidden assumption:** `strict` assumes every required field is a string (`json.Unmarshal(field, &value)` into a `string`). A future number or bool field would fail with a confusing type error. Say so in the name, or check by type. `schema.go:57`

**simplicity of the solution**
- **Three passes over the same bytes:** a map decode, a struct decode, then one decode per required field. The required check could read the already-decoded struct, or one map pass could do it all. `schema.go:41-66`
- **Two places say what's allowed.** The schema and the args struct tags both list the fields. A tag typo (`json:"itemID"`) would pass the key check and silently leave the field empty. Test that each struct's tags match its schema's `properties`, or build the schema from the struct. `classify.go:11`, `classify.go:23`
- **Three helpers for five fields:** `plainString`, `describedString`, `oneOf`. One `stringField(opts)` or plain literals would read just as well. `schema.go:20-34`

**naming and language**
- **Private names too generic for package `tools`:** `send`, `draft`, `search`, `classify`. Say `sendReply` etc., or `runSendReply`. `send.go:28`
- **`strict` doesn't say what it does.** It decodes and checks arguments. `decodeArgs` or `checkedRun` would be clearer. `schema.go:36`
- **`plainString` reads as "any string"** but means a non-empty string: `nonEmptyString`. `schema.go:20`
- **File names don't match tool names:** `draft.go`/`send.go` hold `draftReply`/`sendReply`. `draft_reply.go` would be easier to find. `internal/tools/`

## Suggested improvements

- Make `strict`'s errors safe to show the model: a wrong type becomes `"itemId" must be a string`, and missing and empty get different messages.
- Panic when the tool is built if the schema has no `properties` or `required`, instead of failing every call.
- Check that the args struct tags match the schema's `properties`, with one table test over the four tools, so a tag typo can't slip through.
- Collapse `strict` to fewer decode passes, and say in its name that it's for string fields only, or support other types.
- Rename the private run functions (`send` → `sendReply`, and the others) and `plainString` → `nonEmptyString`. Consider `draft_reply.go` / `send_reply.go`.
- Move `ReadFile` out of `internal/tools` into `cmd/agent-cli`, and delete the unused `ReadFileToolSpec`.
- When subtask 7 lands, update or drop `// agent := &agent.Agent{}` in `cmd/agent-server/main.go`.
- Give the support tests' event channel some headroom, or drain it, so they don't depend on the exact event count.
