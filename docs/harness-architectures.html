Harness Architectures — High-Level Study

Companion to docs/harness-architectures.md · Sources: anomalyco/opencode, charmbracelet/crush, andrelas6/ai-agent (mine)

TypeScript 1 · opencode

Core idea: a headless server owns all state; every UI is just a client.
opencode: clients are disposable — the server + event bus are the product.

Key mechanics

  • Message = list of parts (text, reasoning, tool-call, file…). Everything the model does is appended as parts; the UI renders parts. The single most important data-model decision.
  • Agent loop in session/prompt.ts + session/processor.ts: build messages → call LLM → consume stream part-by-part → execute tool calls, append results → loop until stop / context overflow → compact.
  • Global event bus: every mutation emits an event; the server re-broadcasts over SSE. Clients never poll.
  • Tools: one file each = zod JSON schema + .txt prompt + execute. MCP tools merge into the registry.
  • LLM abstraction (session/llm/): Vercel AI SDK + native provider runtimes; newer code migrating to Effect for explicit errors/retries/cancellation.
Takeaway: state lives server-side in one event-sourced place; the loop emits parts + events; UI is disposable. Overkill for an MVP — but the parts + event bus model is worth stealing.

Go 2 · crush

Core idea: in-process event-driven monolith. Services own state, a pub/sub broker fans events out, the TUI is a Bubble Tea subscriber.
crush: everything is a service behind an interface; the broker decouples loop from UI.

Key mechanics

  • Coordinator interface (internal/agent/coordinator.go): Run(ctx, sessionID, prompt, attachments…). sessionAgent runs the loop on top of agent.Stream(...); token deltas update the assistant message in sqlite; tool calls execute through the permission gate.
  • Everything is a service with an interface — constructed once in app.New, easy to fake in tests.
  • pubsub broker (internal/pubsub): typed channels, lossy for high-frequency deltas, must-deliver for terminal events. Exactly the right Go-shaped design.
  • TUI = pure subscriber: Bubble Tea Elm loop consumes tea.Msg; permissions arrive as dialog events.
  • Persistence: sqlite via sqlc. Bonus: internal/server exposes REST over a unix socket for headless/client mode.
Takeaway: the closest template for your project — same language, proven shape. Interfaces + sqlite + one broker + Bubble Tea. You don't need fantasy: a thin Provider interface over the Anthropic/OpenAI Go SDKs is enough.

Python 3 · ai-agent (mine)

Core idea: the irreducible minimum — one synchronous while-loop.
ai-agent: the entire harness in one loop — everything else is refinement.

What it has — all a harness fundamentally needs

  • Agentic loop with iteration cap
  • Hand-written JSON schemas (llm/available_functions.py)
  • Dynamic dispatch via function_map dict
  • Working-directory sandboxing inside each tool

What it lacks — what opencode/crush add

  • Streaming (prints only at the end)
  • A UI layer separate from the loop
  • Events (the UI can't observe progress)
  • Persistence / sessions · Permissions / human-in-the-loop
  • Subagents, MCP, LSP, compaction

Conclusion — the Go MVP path

The natural evolution: ai-agent's loop, restructured crush-style.

  1. Provider interface (stream, tools) — one impl first (Anthropic or OpenRouter)
  2. Tool interface: Schema() / Execute(ctx, args) → result — port your 4 tools
  3. Agent loop: stream → dispatch tools → append parts → repeat, with ctx cancel
  4. In-process event broker (channels) so UI ≠ loop from day one
  5. Bubble Tea TUI as a subscriber
  6. sqlite persistence + permission gate last

Skip for MVP: MCP, LSP, subagents, compaction, client/server split, plugins.
