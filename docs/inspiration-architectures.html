Anatomy of a harness

The reference shape all three instantiate. Commands travel down through a transport; the agent loop sits in the runtime with tools on one side and the provider on the other; events travel back up through a bus. The three figures below keep these rows in the same order.

crush — Charm's Go harness

All rows present. One binary: the TUI is a client of a server on a Unix socket; the server hosts one App per workspace; App wires services, the agent, and a generic event broker. In "local mode" the same App runs inside the TUI process.

github.com/charmbracelet/crush · Go · internal/ ≈ 100k LOC

Components

cmd/
Cobra: root (TUI), run, server, login, models
ui/
Bubble Tea v2; consumes events, calls the client
client/ proto/
HTTP client + shared JSON types for /v1/*
server/
net/http mux on a Unix socket; streams events
backend/
Hosts N workspaces × M clients; idle shutdown
app/
App struct: opens DB, builds every service, coordinator, LSP, MCP, brokers
agent/
Coordinator + SessionAgent + tools/ + prompt templates
pubsub/
Generic Broker[T] with must-deliver mode
permission/ question/ hooks/
Human-in-the-loop and user shell hooks
db/
SQL → sqlc → typed Go; migrations in the binary

opencode — server-first platform

Same rows, but the server is the product and every UI is a client. Packages enforce the direction: schema → core / protocol → server; clients depend only on schema + protocol. The runtime is Effect services wired as layers.

github.com/anomalyco/opencode · TypeScript on Bun · 27 packages

Abstractions on the edges

Four edges leave the agent loop. Each harness names the interface on that edge differently, but the edge is the same — and the message/part data model is what crosses all four.

→

Proposed Go package map

A synthesis, not a decision: crush's package layout and broker, opencode's part-based messages and loop outcome, ai-agent's sandbox conventions — in-process first, with the wiring kept so a socket server can be added in front later.

Interfaces to write first

type Part interface{ partType() }          // Text · Reasoning · ToolCall · ToolResult · File
type Message struct{ ID, SessionID, Role; Parts []Part }

type Tool interface {
    Info() ToolInfo                           // name, description, JSON schema
    Run(ctx context.Context, call ToolCall) (ToolResult, error)
}

type Provider interface {
    Stream(ctx context.Context, req Request) (<-chan StreamEvent, error)
}

type Broker[T any] interface {
    Publish(EventType, T)
    Subscribe(ctx context.Context) <-chan Event[T]
}

type Runner interface {
    Run(ctx context.Context, sessionID, prompt string) (Outcome, error)
    Cancel(sessionID string)
}

Borrowed from

opencode
Message as typed parts; loop outcome stop | continue | compact; permission as rules
crush
Package layout; Broker[T]; small per-package service interfaces; Tool{Info, Run} with markdown descriptions; in-process first
ai-agent
Path jail on every tool; errors returned as strings; output truncation; iteration cap — and the fix: append every tool result
